## 1. 처음 확인한 현상: 실행보다 먼저 줄을 서는 요청

`worksheet_generations` 조회 결과는 다음과 같았다. 모든 행은 `SUCCEEDED / COMPLETED`였고 `error_code`는 NULL이었다.

| ID | 실행 전 대기 wait_sec | 실행 run_sec |
|---:|---:|---:|
| 99 | 0.4 | 80.8 |
| 100 | 0.0 | 78.4 |
| 101 | 0.1 | 66.8 |
| 102 | 0.1 | 64.5 |
| 103 | 0.3 | 68.2 |
| 104 | 0.1 | 62.5 |
| 105 | 62.5 | 72.7 |
| 106 | 67.3 | 55.5 |
| 107 | 122.0 | 67.7 |
| 108 | 0.0 | 68.3 |

105~107은 시작하기 전부터 약 1~2분 기다렸다. 예를 들어 107은 대기 122초와 실행 67.7초를 합쳐 약 189.7초가 걸렸다. DB 실행 시간이 0.00초로 표시된 것은 이 조회 SQL의 실행 시간이며, 첨삭 처리 속도가 아니다.

코드의 기본 워커 수는 2개다. 실제 API 로그에서도 `generation-1`과 `generation-2`가 작업을 이어받았다. 한 첨삭은 이미지 전사와 첨삭 API를 순차 호출하며 그동안 워커를 점유한다. 두 자리가 사용 중이면 다음 작업은 대기한다.

대기열 기본값 16은 동시에 처리할 개수가 아니다. 대기열이 가득 차 실행기에 제출되지 못한 작업은 DB의 PENDING 상태에서 다시 배정될 수 있다.

## 2. 외부 API 호출이 실행 시간에서 차지한 비중

사용자가 첨부한 `AI_API_CALL` 로그와 SQL의 실행 시간을 연결했다.

| ID | 전사 API 초 | 첨삭 API 초 | API 합계 초 | SQL 실행 초 |
|---:|---:|---:|---:|---:|
| 103 | 17.892 | 43.660 | 61.552 | 68.2 |
| 104 | 19.849 | 35.342 | 55.191 | 62.5 |
| 105 | 18.865 | 36.297 | 55.162 | 72.7 |
| 106 | 18.295 | 35.180 | 53.475 | 55.5 |
| 107 | 26.159 | 38.756 | 64.915 | 67.7 |
| 108 | 22.337 | 38.013 | 60.350 | 68.3 |

- 103~108의 API 합계: 약 350.645초
- 같은 행의 SQL 실행 시간 합계: 약 394.9초
- API 구간이 차지한 비율: 약 88.8%
- 첨부된 103~109의 API 호출 14개: 모두 HTTP 200

호출 구간에는 외부 응답 대기, 네트워크, 로컬 스케줄링 지연 등이 섞일 수 있다. 88.8%를 “순수 모델 계산 비중”으로 해석할 수는 없다. API 실패나 재시도 폭증으로 느려졌다는 증거는 이 로그에 없었다.

핵심은 두 가지다. 작업 하나의 외부 호출이 길고, 그 호출을 기다리는 워커 수가 2개라 동시 요청이 쌓였다.

## 3. 최초 서버 메모리 상태

### 컨테이너 관측

| 대상 | 당시 관측 사용량 / 상한 |
|---|---|
| 개발 Spring | 약 511.6~511.8 / 512MiB |
| 운영 Spring | 약 212.6 / 700MiB |
| MySQL | 약 111.7~112.1 / 400MiB |
| Nginx | 약 12.14 / 100MiB |

개발 컨테이너 CPU는 당시 약 0.14~0.17%였다. 낮은 CPU만으로 RAM 여유나 처리량 여유를 판단할 수 없다.

호스트의 최초 `free -h` 결과는 RAM 약 1.8GiB, available 약 560MiB, 스왑 사용 약 707MiB였다. 이후 테스트 준비 시점에는 available 약 635MiB, 스왑 사용 약 400MiB가 관측됐다. 서로 다른 시점의 값이다.

스왑 사용량은 호스트 전체 값이다. 개발 컨테이너 혼자 쓴 양이나 현재 초당 스왑 입출력을 뜻하지 않는다. 또한 `docker stats`의 BLOCK I/O 3.6GB 등은 누적량이며 현재 디스크 속도나 스왑 발생의 직접 증거가 아니다.

### 최초 cgroup 이벤트

`memory.events`에서 다음 값이 확인됐다.

```text
max 13378
oom 0
oom_kill 0
sock_throttled 88288
```

상한에 걸린 이력과 소켓 메모리 제한 관련 이벤트가 있었다. 누적값이므로 특정 요청 하나의 횟수나 시간으로 환산할 수 없다. 당시 OOM kill이 관측되지 않았다는 사실만 확인됐다. 컨테이너가 재생성되면 이전 컨테이너의 카운터와 직접 비교할 수 없다.

## 4. JVM 내부를 처음 확인했을 때

런타임 이미지에는 `jcmd`가 없어 별도 JDK 진단 컨테이너를 사용했다.

성공한 `GC.heap_info`의 주요 값:

| 영역 | 사용량 / 확보량 |
|---|---|
| young generation | used 18974K / total 118016K |
| old generation | used 211708K / total 262144K |
| 사용 가능한 힙 합계 | 약 371.25MiB |
| 힙 사용량 합계 | 약 225.28MiB |
| 사용 가능한 힙 안의 빈 공간 | 약 145.98MiB |
| Metaspace | used 약 136.65MiB / committed 약 137.75MiB |

Serial GC가 복사용으로 두는 survivor 공간 약 12.75MiB를 포함하면 전체 힙 확보 규모는 약 384MiB였다.

Metaspace의 reserved 약 1152MiB는 가상 주소 공간 예약이다. 실제 RAM을 그만큼 사용했다는 뜻이 아니다. 출력에 함께 나오는 class space는 Metaspace의 일부이므로 다시 더하지 않는다.

이 시점에는 컨테이너 사용량이 거의 512MiB였어도 JVM 힙 안에 빈 공간이 있었다. 하지만 빈 힙 일부도 RAM에 남을 수 있고 힙 밖의 클래스·스레드·버퍼도 메모리를 사용한다. 힙 여유와 컨테이너 RAM 여유는 서로 다른 값이다.

## 5. 원래 설정: 512MiB·힙 최대 384MiB·워커 2개

서버는 계속 실행 중이었고 측정 전 수십 분간 직접 요청이 거의 없었다고 확인됐다. 재배포 직후 첫 요청이라고 가정하지 않는다.

### 이미지 업로드

| SEC | HEAP_USED | HEAP_FREE | META_USED | YGC | FGC | GC_SEC |
|---:|---:|---:|---:|---:|---:|---:|
| 79.6 | 77.9 | 46.0 | 110.6 | 1 | 0 | 0.013 |
| 80.6 | 130.0 | 71.9 | 114.3 | 6 | 1 | 0.283 |
| 81.6 | 181.6 | 20.3 | 114.3 | 13 | 1 | 0.292 |
| 85.7 | 90.3 | 111.7 | 122.7 | 18 | 2 | 0.517 |

이미지를 디코딩하면 압축 파일 크기보다 많은 메모리를 사용할 수 있다. 이 프로젝트는 최대 20MiB·4천만 픽셀을 허용하고 ARGB 이미지 및 PNG 버퍼를 만든다. 이미지 준비와 전송용 데이터 생성은 일시적으로 큰 메모리를 사용할 수 있다.

79.6~85.7초 구간에서 GC 시간은 약 0.504초 증가했다. 업로드 시 힙 사용량과 확보한 힙 크기가 함께 증가했다.

### 첨삭 2개 동시 요청

이미지 업로드는 미리 끝내고 첨삭만 두 개 시작한 조건이었다.

310.3~322.8초의 약 12.5초 동안 GC 누적 시간이 약 9.274초 증가했다. 해당 구간에서 메모리 회수 부담이 컸다는 강한 단서다.

이는 9.274초가 순수 GC CPU 계산 시간이라는 뜻이나 모든 요청이 정확히 그만큼 멈췄다는 뜻은 아니다. OS 대기, 샘플링 시점, 진행 중인 GC 카운터 갱신이 섞일 수 있다. 정확한 정지 구간과 원인 분리는 GC·safepoint 로그 및 스왑 입출력 자료가 더 필요하다.

## 6. 768MiB·힙 최대 512MiB·워커 2개

두 이미지 업로드를 먼저 완료하고 첨삭 두 개를 시작했다.

| SEC | 상황 메모 | HEAP_USED | HEAP_FREE | META_USED | FGC | GC_SEC |
|---:|---|---:|---:|---:|---:|---:|
| 124.1 | 업로드 전 | 77.9 | 46.0 | 112.7 | 0 | 0.043 |
| 127.1 | 업로드 중 | 171.6 | 42.2 | 117.6 | 1 | 0.312 |
| 145.7 | 첨삭 시작 직전 부근 | 188.7 | 184.7 | 124.5 | 3 | 0.822 |
| 147.7 | 증가 구간 | 320.5 | 68.9 | 127.5 | 4 | 0.861 |
| 148.2 | GC 후 | 196.2 | 177.1 | 127.5 | 4 | 1.106 |
| 204.7 | 완료 부근 | 321.7 | 106.4 | 128.5 | 5 | 1.355 |

145.7~204.7초의 59초 구간에서 GC 시간은 약 0.533초 증가했다. 최초 두 요청 관측의 수초짜리 GC 증가와 비교해 지연이 크게 줄어든 모습이었다. 입력 조건과 구간이 완전히 동일한 통제 실험은 아니므로 개선 배수를 확정하지 않는다.

별도로 보고된 컨테이너 사용량은 약 716.1 / 768MiB(93.24%)였다. 표시상 상한까지 약 51.9MiB가 남았다. CPU는 관측상 잠깐 약 30%까지 올라갔다가 내려왔다고 보고됐다. JVM 로그와 컨테이너 수치는 동일 타임스탬프로 묶인 자료가 아니다.

이 단계에서는 워커 추가보다 컨테이너 전체 여유를 먼저 확인하기로 했다.

## 7. 896MiB·힙 최대 512MiB·워커 2개

이 단계의 컨테이너 상한 변경에는 재시작 없는 `docker update` 방법을 안내했다. 런타임 상한 변경은 Compose 파일에 자동 저장되지 않는다.

| SEC | HEAP_USED | HEAP_FREE | META_USED | FGC | GC_SEC |
|---:|---:|---:|---:|---:|---:|
| 47.1 | 287.9 | 149.0 | 132.2 | 1 | 0.278 |
| 52.6 | 403.6 | 33.3 | 132.3 | 2 | 0.290 |
| 53.1 | 265.8 | 171.1 | 132.4 | 2 | 0.498 |
| 72.2 | 421.1 | 15.7 | 132.6 | 3 | 0.519 |
| 72.7 | 284.7 | 205.7 | 132.6 | 3 | 0.724 |
| 76.2 | 285.4 | 204.9 | 132.6 | 3 | 0.724 |

- 제공된 47.1~76.2초 구간: 약 29.1초, GC 시간 증가 약 0.446초, Full GC 2회 증가.
- 중간의 421.1MiB 사용은 당시 사용 가능 힙 약 436.8MiB 기준 약 96.4%였다. 최대 힙 512MiB의 96.4%가 아니다.
- 이후 힙 사용은 약 284.7MiB로 감소했고 사용 가능 힙은 약 490.4MiB까지 확대됐다.
- 컨테이너는 약 735.2MiB, 종료 부근 약 746.9MiB가 보고됐다. 종료 시 표시상 상한까지 약 149.1MiB가 남았다.

제공 구간의 GC 지연은 짧았고 컨테이너 여유가 늘었다. 첨삭 전체의 끝 시점 JVM 로그와 정확한 요청별 완료 시간은 제공되지 않았다.

## 8. 896MiB·힙 최대 512MiB·워커 3개

환경변수 `APP_GENERATION_WORKERCOUNT: "3"`을 테스트 Compose에 넣고 개발 컨테이너를 재생성하는 방법을 사용했다. 이후 사용자는 세 요청이 모두 완료됐다고 보고했다.

| SEC | HEAP_USED | HEAP_FREE | META_USED | YGC | FGC | GC_SEC |
|---:|---:|---:|---:|---:|---:|---:|
| 76.2 | 275.3 | 109.4 | 127.3 | 40 | 5 | 1.317 |
| 77.7 | 312.2 | 182.7 | 127.9 | 42 | 6 | 1.555 |
| 83.7 | 370.5 | 124.5 | 128.2 | 45 | 7 | 1.801 |
| 119.7 | 396.9 | 98.0 | 128.3 | 47 | 8 | 2.030 |
| 125.7 | 410.3 | 84.7 | 128.3 | 48 | 9 | 2.030 |
| 126.2 | 217.7 | 277.2 | 130.8 | 48 | 9 | 2.250 |
| 129.2 | 221.7 | 273.3 | 130.8 | 48 | 9 | 2.250 |

제공된 약 53초 구간에서 GC 시간은 0.933초 증가했다. Full GC는 5→9이므로 이 구간의 증가는 4회다. 힙 사용량은 410.3→217.7MiB로 약 192.6MiB 감소했다.

위 값은 관측 구간의 수치이며, 세 요청 전체의 정확한 처리 시간이나 전체 GC 시간을 뜻하지 않는다.

| 시점 | CPU 관측 | 컨테이너 사용량 |
|---|---:|---|
| 처리 중 | 89.74% | 777.5 / 896MiB |
| 세 요청 완료 부근 | 0.15% | 781.2 / 896MiB |

종료 부근 표시상 여유는 약 114.8MiB였다. 종료 후 높은 사용량이 유지되는 것은 JVM이 확보한 힙 등을 재사용하려고 유지하는 현상과 양립한다. 약 781MiB 전부가 현재 첨삭 데이터나 메모리 누수라는 뜻은 아니다.

CPU는 이전보다 높은 순간 값이 관측됐다. 이 값이 계속 유지됐는지와 호스트 전체 CPU 상황은 기록되지 않았다. 한 샘플로 CPU 병목을 확정하지 않는다.

## 9. 전체 비교와 현재 판단

| 조건 | 제공 구간 GC 증가 | 컨테이너 보고값 | 판단 |
|---|---|---|---|
| 512 / 힙 384 / 워커 2 | 12.5초 구간에서 약 9.274초 | 약 512MiB 상한 근접 | 긴 GC 증가와 대기가 관측됨 |
| 768 / 힙 512 / 워커 2 | 59초 구간에서 약 0.533초 | 약 716.1MiB | GC는 개선됐으나 상한 여유가 작음 |
| 896 / 힙 512 / 워커 2 | 29.1초 구간에서 약 0.446초 | 종료 부근 약 746.9MiB | 컨테이너 여유가 늘어남 |
| 896 / 힙 512 / 워커 3 | 53초 구간에서 약 0.933초 | 종료 부근 약 781.2MiB | 세 요청 완료, 운영 후보로 검토 가능 |

각 행의 입력·시작 메모리·워밍업·관측 구간이 동일하지 않다. GC 시간이나 메모리 사용량을 단순 비율로 비교해 “몇 배 빨라졌다” 또는 “워커 하나당 34MiB”라고 결론내리지 않는다.

아직 확인하지 못한 항목:

- 워커 2개와 3개의 동일 조건 요청별 지연 및 단위 시간당 완료 개수
- 부하 중 호스트 available 최저값과 실제 스왑 입출력
- 지속적으로 세 작업을 처리할 때의 장기적인 메모리·GC 변화
- 큰 이미지와 새 업로드가 첨삭 중 겹치는 조건
- 최종 구성인 개발 512MiB·운영 896MiB에서의 실제 운영 측정

약 1.8GiB 호스트에서 개발 512 + 운영 896 + MySQL 400 + Nginx 100의 상한 합계는 1908MiB다. 상한은 예약 RAM이 아니지만 모든 컨테이너가 상한까지 동시에 쓰는 상황을 보장할 수는 없다. OS 및 기타 프로세스 여유도 고려해야 한다.

최종 후보는 운영 896MiB·힙 최대 512MiB·워커 3개다. 개발은 512MiB·힙 최대 384MiB·워커 2개로 원복하는 계획이다.

## 10. 개선 방향

이번에는 소스 코드를 바꾸지 않고 자원·워커 설정만 조절했다. 추가 개선을 검토한다면 다음 순서가 유용하다.

1. 실제 처리량과 대기 시간을 먼저 비교한다. 세 개를 90초에 처리하는 것이 두 개를 60초에 처리하는 것보다 처리량이 높은 것은 아니다.
2. 큰 이미지 해상도를 적절히 제한하고, 디코딩·방향 보정·PNG 생성 시의 큰 임시 버퍼를 줄인다.
3. 전사와 첨삭 API에서 생성되는 이미지 Base64·JSON 문자열·바이트 데이터의 중복 생성을 검토한다.
4. 워커 추가 시 메모리뿐 아니라 CPU, 외부 API 제한, DB·연결 자원도 함께 측정한다.
5. 호스트 여유가 부족하면 개발·운영 분리 또는 EC2 RAM 증설을 검토한다.

스왑은 메모리 부족을 완화하는 보조 수단이다. 자주 사용하면 지연이 커질 수 있으므로 처리량 확보를 위해 RAM을 대신하는 전제로 잡지 않는다.
