# B10·B11 수동 AI 인사이트 MVP

- 작성일: 2026-11-28
- 브랜치: feat/116-ai-insight
- 사용자 승인 범위: 명시적 생성·업데이트, 최신 결과 하나 저장·조회, 같은 입력 재사용, 입력량 제한, 첨삭과 공유하는 실행 한도·중복 방지
- 화면 대응: 첨부 이미지의 AI 인사이트 항목(제목·설명)과 다음 수업 추천 포인트. 그래프는 기존 B8/B9 API를 그대로 사용한다.

## 1. 실제 동작

```text
학생 성장리포트 진입
  → GET insights → 저장 결과·상태·갱신 필요 여부 표시 (LLM 호출 없음)
  → 선생님이 생성/업데이트 버튼 선택
  → POST insights/generations
     ├─ 자료 부족: 안내, LLM 호출 없음
     ├─ 동일 입력: 기존 결과 재사용
     ├─ 공유 슬롯 없음/다른 인사이트 생성 중: 즉시 503, 수동 재시도
     └─ 실행 가능: 스냅샷을 한 개씩 읽어 발췌 → LLM 1회 → 구조·근거 검증
        → 최신 후보 재검사 → 학생별 결과 한 행 저장 → 결과 응답
```

POST는 동기 응답이다. 프런트는 응답을 기다리는 동안 버튼을 잠그고 로딩을 표시한다. 생성 요청의 클라이언트 timeout은 백엔드의 60초 제한과 네트워크 여유를 고려하고, POST 자동 재시도는 하지 않는다. 새로운 완료본이 들어오면 GET의 isStale이 바뀌지만 자동 생성하지 않는다. 자동 대기열·예약 실행·자동 재시도·작업 복구·과거 분석 이력·별도 인사이트 워커는 구현하지 않았다.

## 2. API

| 메서드·경로 | 역할 |
| --- | --- |
| GET /api/v1/students/{studentId}/insights | 저장된 결과와 후보 개수·미생성/자료 부족·최신 여부 조회 |
| POST /api/v1/students/{studentId}/insights/generations | Body 없이 수동 생성·업데이트. 동일 입력은 재사용. 완료 응답 200 |

같은 기관 원장·선생님이 사용할 수 있다. 타 기관·없는 학생은 동일한 404/STUDENT_001, 미인증 401, 허용되지 않은 역할은 403이다.

## 3. 분석 자료와 제한

- 최근 3개월(KST 오늘의 3개월 전 00:00 이상, 내일 00:00 미만), 완료일·학습지 ID 최신순 최대 10개 후보를 먼저 조회한다.
- COMPLETED·미삭제·저장본 존재·TERRA/SUCCEEDED 작업·원본 해시 일치 조건이다. FIXED/LEGACY_MOCK·미저장·임시저장·삭제·기간 밖은 제외한다. 그래프의 전체 완료 건수와 후보 건수가 다를 수 있다.
- 분석 가능한 정상 저장본이 최소 3개 필요하다. 후보 3개 중 손상된 저장본을 제외하고 2개면 INSUFFICIENT_DATA, usedResultCount=2다.
- 스냅샷 schema 1/2의 공개 review에서 활성·적용된 AI 오류/제안과 교사 CORRECTION/SUGGESTION을 읽는다. GENERAL/SUPPLEMENT는 첫 MVP 입력에서 제외한다. 삭제·미적용은 제외하며 수정으로 진부해진 AI 해설도 제외한다.
- 학생 프로필의 이름·연락처, 학습지 제목·파일명/URL·이미지·좌표·삭제 행/복원 데이터·원문 전체 전사는 별도로 전송하지 않는다. 발췌된 피드백 문장에 포함된 이름 등을 자동 익명화하는 기능은 없다.
- 서버는 해당 완료본 전체의 확정 오류·제안·영역·종류별 수를 계산하고, AI에게는 고정 상한의 발췌 근거를 전달한다. 통계가 표본 건수로 바뀌지 않는다. 이 수치는 학생의 모든 오류 수가 아니다.
- 영역·AI/교사별로 제한된 후보를 순회해 완료본당 최대 6개, 총 최대 60개 근거만 보낸다. 원문 120자·현재 피드백 160자·유효 해설 80자 제한, UTF-8 패킷 96KiB 제한이다.
- metadata 선조회는 저장 JSON을 읽지 않는다. 슬롯 획득 후 스냅샷을 한 번에 한 개씩 조회·축약하므로 전체 기간 JSON을 한꺼번에 유지하는 B8 ALL 방식은 사용하지 않는다. 개별 스냅샷 자체가 비정상적으로 크면 그 한 건을 읽는 메모리까지 없어지는 것은 아니다.

## 4. 화면 응답

| 필드 | 의미 |
| --- | --- |
| status | EMPTY / INSUFFICIENT_DATA / NOT_GENERATED / NO_FEEDBACK / READY |
| isStale | 기존 결과가 현재 분석 대상·설정과 달라 갱신이 필요한지 |
| reused | POST에서 같은 입력 결과를 재사용했는지. GET은 false |
| candidateResultCount | 최대 10개의 후보 수. 아직 JSON 해석에 성공한 건수라는 뜻은 아님 |
| usedResultCount | 실제 사용한 정상 저장본 수. 미생성/해석 전 응답은 null |
| minimumResultCount | 3. 인사이트 운영 기준이며 통계적 실력 진단 보장 수치가 아님 |
| analysisFrom / analysisTo / generatedAt | 저장된 분석 범위·생성 시각. 미생성은 현재 기간 |
| insights[] | title / description / area / kind / evidenceIds. 인사이트 최대 3개 |
| coachingPoints[] | content / evidenceIds. 다음 수업 추천 1~2개. 프런트에서 content를 이어 붙여 복사 |
| evidence[] | 실제 출력이 참조한 근거만 반환. id·worksheetId·feedbackId·source·feedbackType·area·completedAt·발췌 원문/피드백/해설 |

화면 데이터 형태 예시:

```json
{
  "insights": [
    {
      "title": "동사 형태 확인",
      "description": "여러 결과물에서 주어에 맞는 동사 형태에 대한 피드백이 반복되었습니다.",
      "area": "GRAMMAR_SPELLING",
      "kind": "ERROR_PATTERN",
      "evidenceIds": ["ai:101:201", "ai:105:238"]
    }
  ],
  "coachingPoints": [
    {"content": "주어를 바꾸며 동사 형태를 비교해 보세요.", "evidenceIds": ["ai:101:201"]},
    {"content": "수정한 문장을 다시 쓰는 연습을 권장합니다.", "evidenceIds": ["ai:105:238"]}
  ]
}
```

위 문장은 응답 형태 예시다. 서버가 고정 문구를 실제 인사이트로 반환하는 구조가 아니다. 전체 공통 봉투의 result 안에 StudentInsightResponse가 들어간다.

## 5. AI 응답 검증

- JSON 중복 키·뒤에 붙인 데이터·알 수 없는 필드·미완료/거절 응답을 거부한다.
- 인사이트 최대 3개, 제목 60자·설명 300자, 추천 1~2개·각 300자 제한이다.
- 각 항목의 evidenceIds는 입력에 있는 중복 없는 1~3개 ID여야 한다. 대표 영역도 근거와 대응해야 한다.
- ERROR_PATTERN은 서로 다른 결과물 2개 이상의 CORRECTION 근거가 필요하다. 단일 글 안의 여러 카드나 SUGGESTION만으로 반복 오류를 주장할 수 없다.
- IMPROVEMENT는 근거에 기반한 지도 제안이지 실력 향상 판정이 아니다. 낮은 건수·피드백 부재만으로 숙련·퇴보·진단을 추측하지 않도록 지시한다.
- 원문·코멘트는 자료이며 그 안의 지시는 실행하지 않는다. 모델이 만든 세부 패턴 이름을 별도의 확정 통계로 저장하지 않는다.
- 저장/조회에는 실제 출력이 사용한 근거만 남긴다. 최대 3×3+2×3=15개 근거다. NO_FEEDBACK은 오류/제안이 없다는 안내이며 AI를 호출하지 않고 캐시한다.

## 6. 실행 한도·동시성

AiExecutionLimiter는 기존 app.generation.worker-count와 같은 전체 실행 예산을 사용하고, 인사이트 동시 실행은 추가로 최대 1개다. 인사이트 전용 워커를 더하지 않았다.

- 첨삭은 claim 전에 슬롯을 얻는다. 거부되면 PENDING을 유지하고 기존 GenerationJobDispatcher가 다시 배정한다. 실패 상태로 바꾸지 않는다.
- 인사이트는 슬롯을 즉시 얻지 못하면 503/INSIGHT_001이다. 인사이트 대기열과 자동 재시도는 없다.
- 슬롯은 정상·실패·시간 초과 모두 반환하며, close 중복 호출도 예산을 늘리지 않는다.
- 학생을 오래 잠그거나 외부 HTTP 대기 동안 DB 트랜잭션을 유지하지 않는다.
- 저장 직전에 학생 행을 잠그고 후보 목록의 hash를 재검사한다. 생성 중 대상이 바뀌면 409/INSIGHT_005로 저장하지 않는다. 이전 성공 결과는 유지한다.
- 동시 한도와 중복 제어는 단일 JVM 기준이다. 다중 인스턴스 전체 상한은 별도 설계가 필요하다. 별도 우선순위 스케줄러는 없어 첨삭에 슬롯을 예약하는 구조는 아니다.
- 이미지 업로드 등 모든 요청의 메모리를 제한하는 장치는 아니다. 실제 혼합 부하의 컨테이너 RAM·GC·첨삭 대기 시간을 측정해야 한다.

## 7. 캐시·DB·설정

입력 hash에는 학생/기관, 후보 ID·revision·schemaVersion·원본 해시·생성 ID·완료일, 정책·프롬프트·모델·출력 토큰 한도가 포함된다. 같으면 기존 결과를 재사용하고 생성 시각/버전을 갱신하지 않는다. 날짜가 바뀌어도 실제 후보가 같으면 재사용하며 기간 이동으로 후보가 제외되면 hash가 달라진다.

새 student_insights 테이블은 학생 PK/FK 하나당 최신 READY/NO_FEEDBACK 결과 한 행을 보관한다. 결과 JSON, 최대 10개 후보 출처, hash, 실제 사용 건수, 모델·프롬프트·스키마 버전, 분석 기간, 생성자·시각, 감사·낙관적 락 필드를 보관한다. 기존 테이블과 학습지 snapshot 구조는 변경하지 않는다. 생성 중/실패 행이나 과거 결과 이력은 보관하지 않는다.

운영 배포 전 `infra/db/2026-11-28_student_insights.sql`을 적용해야 한다. 기존 students/users의 BIGINT 타입과 일치해야 하며 MySQL DDL은 자동 커밋이다. SQL은 운영 DB에서 아직 실행하지 않았다. ERD v3에는 실제 추가한 테이블과 관계만 반영했다.

설정은 AI_INSIGHT_MODEL(기본 기존 첨삭 모델 gpt-6.1-terra), AI_INSIGHT_REQUEST_TIMEOUT(기본 60s, 최대 90s), AI_INSIGHT_MAX_OUTPUT_TOKENS(기본 2400, 최대 4000)이다. endpoint/key는 app.ai.insight.*를 우선하고 기존 app.ai.terra.* 및 OPENAI_API_KEY를 재사용한다. 정상 조회·자료 부족·캐시 재사용에는 키가 없어도 되고 실제 생성 요청에서만 설정 오류를 반환한다.

실제 AI 호출은 텍스트만 보내며 입력 96KiB·수신 본문 256KiB·모델 JSON 16000자 제한이 있다. 본문은 전부 수신한 뒤 검사하지 않고 상한 초과 중에 구독을 취소한다. 헤더/본문 모두 전체 대기 시간을 제한한다. 오류 원문·키·학생 원문은 로그에 쓰지 않고 모델·경과 시간·HTTP 상태만 기록한다. 외부 유료 API 검증은 자동 테스트에 포함하지 않는다.

## 8. 오류

| HTTP / 코드 | 의미 |
| --- | --- |
| 503 / INSIGHT_001 | 전체 슬롯 또는 인사이트 1개 슬롯 사용 중 |
| 503 / INSIGHT_002 | AI endpoint/key 설정 오류 |
| 502 / INSIGHT_003 | 통신·HTTP·전체 timeout·수신량 초과 |
| 502 / INSIGHT_004 | 응답 JSON·근거·반복 패턴 검증 실패·미완료·거절 |
| 409 / INSIGHT_005 | 분석 중 입력/저장본 변경 |
| 500 / INSIGHT_006 | 기존 저장 인사이트 해석 실패 |
| 422 / INSIGHT_007 | 입력량 제한 초과 |

GET은 저장 결과 조회만 수행한다. 생성 실패가 나면 프런트가 오류를 안내하고 GET으로 이전 성공 결과를 다시 보여줄 수 있다. 후보가 최소 3개 미만이면 EMPTY/INSUFFICIENT_DATA 안내를 우선하며 이전 DB 결과 자체를 삭제하지 않는다.

## 9. 검증

API 테스트는 실제 JWT·MVC·커밋된 H2(MySQL 모드)와 가짜 InsightClient를 사용한다. HTTP 계약 테스트는 로컬 가짜 Responses 서버를 사용한다. 학생 권한·수동 생성·GET 무호출·캐시 재사용·새 완료본 stale·실패 보존·동시 중복·공유 예산·입력 변경·정상본 최소 수·고정 자료 제외·최대 10개·GET의 저장본 엔티티 미로딩을 검증한다. 계약 테스트는 미등록 근거·서로 다른 결과물 조건·단일 글 중복·제안의 오류 오인·길이·JSON 구조를 검증한다. 실행 제한 테스트는 거부된 첨삭이 claim되지 않고 다음 실행이 가능한지도 확인한다. SQL 테스트는 기존 학생 보존·PK/FK를 확인한다.

- 전체 회귀: `./gradlew --offline --no-daemon spotlessApply spotlessCheck test` — **102개 스위트·2,371개 테스트, 실패·오류·스킵 0**, BUILD SUCCESSFUL.
- 이후 잘못된 endpoint·인증 헤더 설정 검사 7개를 추가 보완하고 HTTP 계약 클래스 **23개 전체를 재실행하여 통과**했다. 새 설정 경계 보완 후 전체 회귀를 다시 반복하지 않았다.
- 신규 기능 시나리오는 API 14개·응답 계약 17개·공유 실행 한도 3개·SQL 1개·HTTP 23개, 총 **58개**다. 전체 회귀에는 새 ErrorCode를 자동 검증하는 기존 enum 테스트도 포함한다.
- 포맷 검사 및 `git diff --check` 통과. 실제 유료 AI 호출·운영 MySQL 적용·프런트 E2E·컨테이너 혼합 부하 측정은 수행하지 않았다.
