# 수동 재시도·전사 재사용·중복 실행 방지

## 접수 조건

기존 `POST /api/v1/worksheets/{worksheetId}/generations/{generationId}/retry`를 사용한다. 새 작업 ID를 반환하고 커밋 후 워커가 실행한다. 다음 조건이 모두 맞아야 새 재시도를 접수한다.

- 요청자의 현재 DB 학원 소속·활성 여부와 학습지 학원 소속이 맞는다. 대상 작업도 해당 학습지에 속해야 한다.
- 대상이 해당 학습지의 **최신 작업**이며 FAILED, is_retryable=true다. 생성 시간이 같으면 큰 작업 ID를 최신으로 판단한다.
- 학습지가 FAILED이고 접수 당시 원본 파일 해시와 현재 파일 해시가 같다.
- 선택 영역과 영역별 수준이 최초 요청 설정과 같다. 배열 순서는 비교하지 않고, GRAMMAR_MECHANICS 별칭은 GRAMMAR_SPELLING으로 정규화한다. 영역 비활성화·추가 또는 수준 변경은 불일치다.

잘못된 학원/학습지 대상은 404, 요청자 DB 학원 불일치·비활성은 403, 재시도 조건 불일치는 409다. 이미 접수된 동일 요청의 재전송은 작업을 만들지 않고 그 작업의 현재 상태를 반환한다. 재전송도 현재 소유권과 요청자 자격은 확인한다.

## 멱등키와 동시 요청

`Idempotency-Key`는 기존처럼 DB 전체에서 유일하다. 키는 **학습지 + 최초 생성 또는 특정 실패 작업에 대한 재시도**라는 요청 의미와 연결한다.

- 같은 생성 키 재전송은 같은 생성 작업을 반환한다.
- 같은 실패 작업에 같은 재시도 키를 재전송하면 같은 새 작업을 반환한다. 작업이 다시 실패해도 같은 키로 새 작업을 만들지 않는다. 다음 수동 재시도는 새 실패 작업 ID와 새 키를 사용한다.
- 생성 키를 재시도에 사용하거나, 재시도 키를 생성·다른 재시도에 사용하면 GENERATION_007 / 409다. 다른 학습지의 키를 재사용해도 같다.
- 학습지 행 잠금으로 생성·재시도 접수를 직렬화한다. 서로 다른 키로 동시에 접수해도 한 작업만 새로 수락한다. 같은 의미·같은 키면 두 응답 모두 같은 ID를 반환한다.
- 서로 다른 학습지가 같은 키를 동시에 선점하는 경우 DB의 `UK_generation_idempotency_key` 제약이 최종 방어한다. 이 충돌도 500 대신 409를 반환하고, 실패한 접수의 학습지 상태 변경은 롤백한다.
- 워커의 DB claim은 PENDING만 한 번 RUNNING으로 전환한다. 추가 배정이나 같은 ID의 중복 실행은 클라이언트를 호출하지 않는다.

자동 유료 재시도는 추가하지 않았다. PENDING 재배정은 아직 실행을 시작하지 않은 접수를 배정하는 것이며, FAILED 외부 처리를 자동 재호출하는 기능이 아니다.

## 유효한 전사 재사용

각 작업의 nullable `input_transcription_id`에 사용한 불변 전사 ID를 기록한다. 재시도는 이전 작업이 사용한 전사를 참조하므로 첨삭이 연속으로 실패해도 최초 전사를 재사용할 수 있다. 이전 단계의 참조 없는 작업은 해당 생성·페이지의 전사에서 후보를 찾는다.

후보는 **재시도 접수와 실행 직전** 다음을 검사한다.

- 전사 생성 학원·학습지와 현재 작업 소속, 페이지 ID·번호
- 접수 파일 해시와 현재 원본 파일 해시
- 현재 보정 PNG 해시·가로·세로와 전사의 이미지 정보
- 기존 실행 경로(FIXED/LEGACY_MOCK), 모델, 정규화 버전
- 전사 원문에 대한 SHA-256 텍스트 해시와 줄 구성

검사가 통과하면 OCR 클라이언트를 호출하지 않고 AI_CORRECTION부터 실행한다. 전사가 없거나 무결성이 맞지 않으면 OCR로 새 전사를 만든다. 워커는 현재 PNG를 다시 조회하며 두 단계에 같은 PNG를 사용한다. 다른 학원·학습지의 전사를 가져와 재사용하지 않는다.

재시도는 이전 실행 경로를 유지한다. 서버의 고정 모드 설정이 바뀌어도 기존 실패 작업의 모델 경로가 바뀌지 않는다. 생성 결과는 새 작업 ID와 기존 불변 전사 ID를 함께 참조하고, 카드 anchor도 같은 전사 ID를 사용한다. 이전 전사·원본 응답·검증 결과는 덮어쓰지 않는다.

## 늦은 완료 방어

전사 저장·첨삭 결과 저장·실패 처리에는 학습지 → 작업 순서의 잠금을 사용한다. 결과는 RUNNING, 예상 단계, 최신 작업, 학습지 PROCESSING을 확인한 뒤 저장한다.

중단된 이전 워커가 새 재시도 완료 후 성공·실패 응답을 반환해도 이전 실패 상태와 새 카드·학습지 READY를 변경하지 않는다. 서버 재시작 복구의 단일 서버 전제는 [백그라운드 작업 문서](AI-백그라운드-생성작업.md)와 같다.

## 로컬 확인

```powershell
$env:JAVA_HOME = 'C:\Users\82108\.jdks\temurin-21.0.11-1'
.\gradlew.bat --offline -I scripts/local-h2-tests.init.gradle test --tests '*FixedResponseReviewApiTest'
```

H2·임시 PNG·고정 클라이언트만 사용한다. 단계별 실패 후 수동 재시도, 전사 재사용과 손상 시 OCR 재실행, 소속·최신·파일·수준 검사, 동시 생성/재시도 HTTP 요청, DB 유일키 경합, 늦은 성공/실패를 검증한다. 지연은 latch로 제어해 긴 sleep을 줄인다.

수동 API 확인 시 AI_CORRECTION 실패를 만든 뒤 새 키로 retry를 요청한다. 성공 결과의 전사 ID와 카드 anchor가 실패 작업의 전사 ID를 유지하는지 확인한다. 같은 키 재전송의 작업 ID는 같아야 하며, 다른 키로 진행 중인 작업에 추가 재시도하면 409다.

실패 작업의 전사 참조는 로컬 DB에서 `select id, status, current_stage, input_transcription_id, retry_of_generation_id from worksheet_generations where worksheet_id = ? order by id`로 확인한다. 성공 결과의 `/review`에는 `aiResults[].transcriptionId`와 `corrections[].anchor.transcriptionId`가 포함된다.

## 검증 결과

- 변경 기능에 직접 관련된 H2 통합 테스트 25건을 먼저 실행해 모두 통과했다. 기존 13건을 유지·보완하고 전사 재사용·가드·동시 요청·늦은 완료 사례 12건을 추가했다.
- 단계 연결 후 전체 검사는 한 번 실행했다. 18개 클래스, 325건 통과. 실패·오류·건너뜀 0건. `build`, `spotlessCheck`, `git diff --check`도 통과했다.
- 동시에 들어오는 같은 키 생성, 같은 키 재시도, 다른 키 재시도, 생성과 재시도 혼합, 서로 다른 학습지의 전역 키 경합을 실제 MVC·H2 경계에서 확인했다. 이전 워커의 늦은 성공·실패 후에도 새 결과가 유지됐다.
- 실제 AI·유료 실험 main, 실제 MySQL의 잠금 경합·다중 서버·부하·강제 종료 검증은 생략했다. 공유·운영 DB 변경과 커밋·push·PR·병합은 수행하지 않았다.

## 남긴 범위

후속 단계에서 [Terra HTTP 어댑터](AI-Terra-HTTP-클라이언트.md)를 연결했으며, TERRA 전사에도 동일한 재사용 검사를 적용한다. 자동 유료 재시도·다중 서버 lease/heartbeat는 연결하지 않았다. 공유·운영 DB에도 적용하지 않았다. 운영 반영 전 `input_transcription_id` 열 추가와 기존 멱등키 유일 제약의 명시적 이름 이관이 필요하다. 전사 참조는 논리 ID이며, 저장·재사용 경계에서 연결을 검증하고 결과 아카이브의 전사 FK와 함께 보존한다.
